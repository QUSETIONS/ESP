# ESP 单体仓库发布设计

## 目标

将现有 `zectrix` Git 仓库作为正式单体仓库发布到
`https://github.com/QUSETIONS/ESP`，保留已有提交历史和当前开发成果。

## 仓库边界

仓库根目录保持不变，包含以下产品代码：

- `main/`：ESP32-S3 固件及板级、显示、BLE、会议功能。
- `tools/meeting_server/`：后台服务、浏览器管理页面、会议和便签接口、录音与实时摘要。
- `tools/wechat_miniprogram/`：微信小程序客户端。
- `tools/ble_meeting_sync/`：BLE 数据同步和调试工具。
- `tools/tests/`：固件契约、后台接口和配套工具测试。
- `docs/`、`scripts/`、`partitions/`：项目文档、构建工具与分区配置。

外层工作区中的付款材料、会议文件、参考图片、原始压缩包和结构件不进入仓库。

## 历史与目录策略

保留现有 Git 历史，不重新初始化仓库，也不批量移动为
`firmware/`、`backend/` 等新目录。这样可避免破坏构建脚本、测试中的相对路径和既有提交追踪。

## 发布流程

1. 检查待提交文件中的凭据、私钥、Wi-Fi 密码、访问令牌和运行数据。
2. 完善忽略规则，确保构建产物、缓存、后台运行状态和本机环境文件不进入版本控制。
3. 为单体仓库补充根目录说明，标明固件、后台和管理入口。
4. 运行与变更风险相称的测试，并检查 Git 状态和待提交差异。
5. 将现有开发成果提交到当前分支。
6. 将 GitHub 地址配置为 `origin`；先获取远程状态，确认不会覆盖远程已有历史。
7. 在远程为空或历史兼容时推送；若远程已有冲突历史，停止并报告，不强制覆盖。

## 安全与失败处理

- 不提交 `.env`、后台状态目录、缓存或生成日志。
- 不使用强制推送。
- 不改写现有提交历史。
- GitHub 鉴权不可用时，保留完整本地提交并给出明确的认证入口。
- 测试失败时不宣称发布完成；记录失败项并区分既有问题和本次整理引入的问题。

## 验收标准

- 一个 Git 仓库同时追踪固件、后台管理端和配套客户端。
- 外层非项目资料没有被纳入追踪。
- 敏感信息和运行时数据未进入待推送提交。
- 根目录说明能够指导开发者定位固件与后台并启动后台管理页面。
- 本地提交完整，且 `origin` 指向 `https://github.com/QUSETIONS/ESP`。
- GitHub 推送成功，或仅因用户侧认证而留下清晰、可继续执行的交接状态。
